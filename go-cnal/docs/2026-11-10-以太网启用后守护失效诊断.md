# 2026-11-10：启用以太网后 v6 断、v4 不自动连、手动重连无效

> **⚠ 2026-11-11 修正：本文 §0 的根因结论与 §3 的修复判据均已被真机复测否证，
> 详见 `2026-11-11-根因修正与门户选源设计.md`。**要点：`1.1.1.2` **不是**
> Cloudflare，而是汕头大学门户服务器的真实地址（实测证书 `CN=*.stu.edu.cn`，
> 系统信任库校验通过）；§3 加的「公共解析器地址一律拒绝钉 IP」黑名单把**真门户**
> 挡在门外，须撤销。真正的根因是「物理源按路由表选 → 插线后选中以太网，而校园
> 认证网关只在 WLAN 网段可达」。本文保留原文作为过程记录，不改写历史。

> 用户操作：Win+X → 设备管理器 → 网络适配器 → Realtek PCIe GbE → 启用。
> 之后 IPv6 连不上、IPv4 不自动连、点「立即检测重连」无效，只有浏览器
> 手动能连。安卓版开发暂停，先查本机。
> 全程只读诊断（不改守护配置、不动网卡、不重启服务），修复另起一节。

## 0. 结论（一句话）

**FlClash 的 DNS 分流按「源地址」对绑物理源的查询返回了公共 DNS 地址
`1.1.1.2`，守护把它当成门户真实 IP 钉死，把登录/探测请求发往 Cloudflare
DNS；浏览器不钉 IP、走 fake-ip 经代理反而正常。** 启用有线网卡改变了多网卡
选路，但决定性破坏是 DNS 污染与「代理接管全部出口」的拓扑冲突。

## 2. 被实测否证的两版判据（保留，供以后参考）

1. 初判「守护绑到以太网源导致门户不可达」→ `/state` 显示 v4 源已切回
   WLAN，且以太网/WLAN 绑源 TCP 443 **都** TIMEOUT，只有 AUTO（走 FlClash）
   CONNECT OK。否证。
2. 再判「绑源 DNS 解析失败导致 pin 为空」→ `ResolveBound` **成功**返回
   `1.1.1.2`。否证。

**「立即检测重连」为什么没用**（读码确认）：`a.Login` → `p.action.Do()` →
`deliverPinned` 第一步 `p.pin()` 就是 `1.1.1.2:443`。手动重连**确实越过了
自动闸**（`compose_api.go:38`），不是被节流拦住；日志里的「登录节流」是
自动 tick 的 `d.lastLogin + loginMinInterval`。两条路殊途同归，都栽在钉错
IP + 绑物理源直连。

## 3. 修复（用户选定：绑源 DNS 结果校验）

`internal/netstack/resolver.go` 的 `ResolveBound` 增加可信性过滤，命中即
fail-closed 并带明确原因：

- fake-ip 段（既有）、回环、链路本地、未指定、组播、非全局单播（保留段）；
- **显式列举的知名公共 DNS 解析器**（Cloudflare / Google / Quad9 / OpenDNS /
  阿里 / 腾讯 / 114DNS）——它们永远不可能是校园门户，是 DNS 劫持的典型落点。

为什么用显式集合而不是「按地址形状猜」：实测 `1.1.1.2`、`8.8.8.8`、
`28.0.0.136` 都是 `IsGlobalUnicast=true`，而校园内网 IP 与公网门户 IP 也
都是全局单播——单看 IP 属性无法区分，硬编码形状会误伤。显式集合误伤面
可控，`TestResolveBoundReturnsRealIP` 覆盖了校园内网 / 教育网公网 / IPv6
全局地址不回归。

验证（tdd 垂直切片 + 变异检查）：
- RED：4 个公共解析器地址都被旧代码当成真门户返回；
- GREEN：全部拒绝且错误原因含「劫持」；
- 变异：删掉校验，测试立刻报红，改回通过；
- **真实环境复验**：对当前真实校园 DNS 跑修复后的 `ResolveBound`，输出
  `DNS 应答疑似被劫持/污染（1 个地址全部落在 fake-ip、公共解析器或保留段），拒绝钉 IP`；
- 全量门：`go test ./...` / `go vet ./...` / android 交叉编译 / 浏览器 a11y 全绿。

## 4. 修复的边界（不夸大）

**这个修复不恢复联网。** 它做到的是：
- 不再把账号密码发往 `1.1.1.2`（凭据纪律）；
- 失败原因从「认证服务器不可达 / 登录被拒」变成明确的「DNS 应答被劫持」，
  下次查得动；
- 门户钉 IP 在污染期间 fail-closed，不猜地址。

用户网络仍不通，因为 FlClash 接管下「绑物理源直连」本来就走不通。要恢复
自动守护，需要另做「代理拓扑感知」或调整本机网络（下文），**本轮未做**。

## 5. 恢复联网的候选（未实施，需用户决定）

1. **临时禁用以太网**（回到启用前的单 WLAN 拓扑）——最可能立刻恢复，但
   需用户在设备管理器操作，且未在本轮验证；
2. 调整 FlClash 的 DNS 分流：让对 `10.129.17.10` 的查询不按源改写、或给
   `a.stu.edu.cn` 加直连规则；
3. 守护侧：检测到 DNS 被 TUN 接管时不再绑源钉 IP 直连，改走代理（与浏览器
   同路）——改动大，涉及物理栈纪律与风暴三闸，需单独设计；
4. `config.ini` 的 `bind_ip` 逃生口手工钉 WLAN 源 `172.29.153.208`，可稳定
   物理源，但**解决不了 DNS 污染**（绑源查询仍返回 `1.1.1.2`）。
