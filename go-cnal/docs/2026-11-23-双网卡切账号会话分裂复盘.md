# 双网卡切账号会话分裂复盘（2026-11-23，用户实测报告 + 当场复现取证）

> 用户报告：「一个账号流量用完了，面板显示还有、点查流量明细数字完全没变；
> 在设置里切换到另一个账号后能查到新账号流量，但浏览器打开 IPv4 门户首页
> 还是旧账号，手动切到 v6 页面发现登录账号是新账号。」
> 本文是**根因已当场复现、证据链完整**的复盘；按用户拍板**先不改代码**，
> 修复方案留待下个版本（v2.4.1）。

## 0. 结论先行

**这不是缓存 bug、不是面板 bug，是双网卡 + 门户按源 IP 记会话的必然结果**：

- 本机有两张可路由网卡：WLAN 2 = `172.29.153.208`（守护绑定源），以太网 = `10.141.53.34`（浏览器默认路由出口）
- 守护切账号只绑 **WLAN 源**做「注销→登录→门户确认」，以太网会话**没人碰**
- 门户按来源 IP 记会话：WLAN 换成了新账号，以太网仍归旧账号
- 浏览器走系统默认路由（以太网 metric 更优）→ 看到旧账号
- 面板流量查的是 WLAN 会话（新账号）→ 看到新账号读数
- 两边都对，只是**地址不同**——这就是「浏览器旧账号 / 面板新账号 / v6 新账号」全部现象的统一解释

## 1. 当场复现取证（2026-11-23 19:47–19:57，证据全部实测）

工具：一次性只读诊断（testdata/diagv4，已删）——对每个本机 v4 源绑源发
`online_check`（与守护 `onlineV4` 完全同款请求，只读、不注销不登录），
门户如实回报「这个地址归哪个账号」。

| 时刻 | 操作 | WLAN 172.29.153.208 | 以太网 10.141.53.34 | /flux 实时（用户名称） |
|---|---|---|---|---|
| 19:47 | 切前基线（当前 23ykyang） | 23ykyang | 23ykyang | 23ykyang 2.41547G |
| 19:54 | API 切到 **23jszeng** | **23jszeng**（已搬） | **23ykyang**（漏网） | 23jszeng 4G「日流量超额」 |
| 19:57 | 用户浏览器打开 IPv4 门户首页 | — | — | **显示 23ykyang**（与以太网诊断一致 ✓） |
| 19:58 | 切回 23ykyang（恢复日常） | 23ykyang | 23ykyang | 23ykyang |

**关键对照**：切到 23jszeng 后，守护日志写「门户确认 v4/v6 都归 23jszeng」
（ WLAN 源属实），但浏览器同时显示 23ykyang（以太网源属实）——日志没错、
用户没错，差异就在源地址。

## 2. 排除的两个错误猜测（prove-it：先证伪再定案）

| 猜测 | 验证方法 | 结果 |
|---|---|---|
| ① 面板「今日流量」缓存不刷新（StoreFluxView 失效） | 点 `/flux` 后等一拍再读 `/state` | ✗ 排除：2.27196G → 2.41547G 一拍内落账正常（`fluxPending`→`pollFlux` 链路工作） |
| ② 切账号后两网卡都归新账号（无分裂） | 首次只读诊断（当前 23ykyang） | 当时确实都归 23ykyang——但那是**切到 23ykyang 之后**的状态；切到 23jszeng 后立刻分裂。教训：**单看一个稳态快照会漏掉时序** |

补充发现：`/state` 的 flux raw 丢弃了「用户名称」字段（`FluxUsage` 只取已知
别名），面板因此无法显示当前读数属于哪个账号——不是 bug，但加剧了用户混淆。

## 3. 为什么会这样（代码层）

`internal/app/switch.go:59-126` 的 `switchAccount`：
- `releaseV4()` → `p.logoutV4(cfg)`（`compose_session.go:186`）只绑守护的物理
  v4 源（当前 = WLAN），对以太网会话不发任何请求
- 认证、门户归属确认（`inspectStacks` → `onlineV4`）同样只看 WLAN 源

`internal/app/compose_portal.go:280` 的 `fluxQuery` 也只绑同一物理源——所以
面板读数与浏览器（以太网）天然可能不一致。

**边界说明**：11-20 之前用户只有 WLAN，浏览器与守护同地址，这问题不存在；
11-22 起「可以连网线用校园网」后才暴露——是**新环境触发的既有设计边界**，
不是 v2.4.0-go 引入的回归。

## 4. 修复方案（用户拍板：留待 v2.4.1）

**方向**：`switchAccount` 扩展为「搬所有本机 v4 会话」——仿照现有 v6 extras
的处理（`releaseV6All` 对同接口所有公网 v6 各注销一次），对每个可路由 v4 源
（WLAN + 以太网）做「探归属 → 注销旧会话 → 登录新账号 → 门户确认」。

**代价与风险**：
- 每切一次多打若干门户请求（每个 v4 源 2–3 次），可能撞门户限频（D6）
- 需确认以太网的 v4 会话能被同款 `logoutV4` 注销（门户按源地址认栈，推测可行但未验）
- 必须真机复测：本双网卡环境现成，切完应看到两源 + 浏览器全部归新账号

**验收判据**（修复后）：切账号后 `diagv4` 类只读诊断显示所有 v4 源归同一账号，
浏览器 IPv4 门户首页显示同一账号，面板流量 = 该账号 userflux 读数。
