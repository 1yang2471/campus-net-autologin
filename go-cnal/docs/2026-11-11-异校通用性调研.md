# 2026-11-11：异校通用性调研（从底层原理能拿到什么）

> 触发：用户问「通用性看看能不能从底层原理想办法获取其它学校校园网的信息」。
> 调研用 agent-reach skill（本机只装了 `rss` / `youtube` 两个渠道，github/web
> 不在 index；按 skill 选路规则用自带搜索/读取工具为主，rss 读了仓库提交 feed）。
> 全文结论都带可回查的原文出处；**不把 README 宣传语当实现证据**，读了源码。

## 0. 一句话

「拿到另一所学校直接能跑」在原理上**只能自动化一半**：**门户在哪、是哪一族
认证系统**可以靠网络层探针 + 页面指纹自动推出来；**这所学校具体怎么提交登录、
密码怎么编码、成功/失败回什么词**推不出来（那是各校部署时的人为约定，不是协议
标准）。可行路线是 **detect 自动出「厂商识别 + 参数抠取 + 配置草稿」→ 人确认
或社区指纹库补全 → 生成 ini**，而不是幻想零配置全自动。

## 1. 底层原理：信息到底藏在哪几层

一次未认证的校园网请求，按 TCP/IP 栈自下而上会依次暴露这些可自动采集的信号：

| 层 | 能被自动观测到的信号 | 能推出什么 | 本项目现状 |
|---|---|---|---|
| 链路/路由 | 默认网关、DHCP 给的 DNS、本机源 IP | 门户候选地址（网关/内网 DNS 常就是门户） | 部分：`campus_dns` 需人填；`default_gateway` 未采集 |
| DNS | 校园 DNS 把门户域名答成哪个 IP（本校实测 `a.stu.edu.cn → 1.1.1.2`） | 门户真实 IP（绕开 TUN fake-ip 的关键） | ✅ `ResolveBound` 绑源解析 |
| HTTP 劫持 | 未认证时 `generate_204` 变 302，`Location` 自报门户 URL（**URL 里的 queryString 是最强指纹**） | 门户地址族、厂商型号、`ac_id`/`wlanuserip`/`jsVersion` 等现场参数 | ✅ `DetectPortal` 解析 `Location`；但只取了基址，丢了 queryString |
| HTTP 响应头 | `Server: DrcomServer1.0` 之类 | 厂商（Dr.COM 等） | ❌ 未读 |
| 登录页正文 | 独特字符串（见 §2 表）、`<title>`、JS 变量名、表单字段 id | 厂商 + 登录表单结构 | 部分：`login_page_marks` 可配，但只做「是/否」验证，不产出配置 |

**关键限制（本校实测，已写进主文 §12.2）**：校园常把 `connect.rom.miui.com`、
`www.msftconnecttest.com` 这类强制门户探测域名**放进白名单**，带这些 Host 的请求在
未认证时也拿到真 204/200/404，永远看不到劫持。所以探测器必须**先不带 Host**、再带
配置 Host，且**不能只信一个锚点**——`campusnet` 的 `detector.py` 也独立踩到同一个坑：
它明确写了「学校经常把探测地址加进白名单，只看第 1 关会误判为已联网」，于是加了
第二关「抓正常网页校验正文标记」。两条独立实现撞到同一堵墙，说明这是底层共性，
不是某校特例。

## 2. 活样本：`demo133/campusnet` 的识别链（读了源码，不是看 README）

出处（2026-11-11 用 anysearch extract 取原文）：

- `campusnet/detector.py`：`HIJACK_PROBES`、`CONTENT_PROBES`、`check_online()`、
  `portal_candidates()`、`detect()`、`_looks_like_portal()`
- `campusnet/providers/__init__.py`：`fingerprint(ctx)` → `[(provider, 置信度)]`，
  按分数降序、低于 `min_confidence` 丢弃，`rank()` 给出「依次尝试」顺序，全不中时
  给保守兜底顺序
- `campusnet/providers/base.py`：`DetectContext{url,response,text,headers}` +
  `has()/has_any()`，Provider 子类实现 `detect(ctx)->float` 与 `login()`
- `docs/providers.md`：厂商指纹表 + 四种协议细节

它的**指纹表**（`docs/providers.md` 原文）：

| Provider | 识别特征（可自动采集） | 登录接口 | 验证情况 |
|---|---|---|---|
| `drcom` | 响应头 `Server: DrcomServer1.0`；页面含 `Dr.COMWebLoginID_0.htm`、`v4serip`、`DDDDD`/`upass` | `GET /drcom/login`（JSONP）+ `POST :801/eportal/?c=ACSetting&a=Login` | ✅ 真实环境实测 |
| `srun` | 页面/URL 含 `srun_portal`、`cgi-bin/get_challenge`；`ac_id` | `GET /cgi-bin/get_challenge` → `GET /cgi-bin/srun_portal` | 已实现，待更多学校验证 |
| `ruijie` | 页面含 `InterFace.do`、`queryString` | `POST /eportal/InterFace.do?method=login` | 已实现，待更多学校验证 |
| `eportal` | 页面含 `c=ACSetting&a=Login`、`wlanuserip` | `POST /eportal/?c=ACSetting&a=Login` | 已实现，待更多学校验证 |
| `eportal_portal` | URL 含 `eportal/portal/login`、`dr1003`、`jsVersion` | `GET /eportal/portal/login`（JSONP `dr1003`） | 已实现，待更多学校验证 |
| `custom` | 不参与识别，必须显式指定 | 模板拼接 | ✅ |

它的 `detect()` 还会从页面/重定向里**正则抠现场参数**（`detector.py` 的 `notes`）：
`ac_id`、`ssid`、`vlan`、`client_ip`(`v46ip|ss5|wlanuserip`)、`portal_ip`(`v4serip`)。
注意 `detector.py` 的一句关键注释——**「302/307 的 Location 往往才是真正带参数的
门户地址…那串参数是最强的指纹，丢了它新版门户就认不出来了」**，所以它会把同源
重定向 URL 补进指纹上下文。这正好点出本项目当前 `parsePortalLocation` 只保留
`scheme+host[:port]`、丢掉 query 的不足。

**它的协议细节也说明了「为什么不能全自动」**：

- 深澜 Srun 要三步：`get_challenge` 拿一次性 challenge → `hmd5=md5(pwd+challenge)`
  → 用**非标准 base64 字母表**（`LVoJPiCN2R8G90yg+hmFHuacZ1OWMnrsSTXkYpUq/3dlbfKwv6xztjI7DeBE45QA`）
  编码 info、再算 `chksum=sha1(...)`。密码字段是 `{MD5}<hmd5>` 而不是明文。
- Dr.COM 传统接口字段叫 `DDDDD`/`upass`，成功判据是 JSONP 里的 `result==1`；
  经典 ACSetting 接口判据是 `<script>Msg=00;...`。
- 锐捷要把门户 URL 里的 `queryString`（`wlanuserip=...&wlanacname=...`）原样回传，
  「抠不到时会退化拼一个，多数学校也能过」。
- 新版 eportal 用账号后缀区分运营商（`@cmcc`/`@unicom`/`@telecom`）。

→ 这些都是**厂商实现细节 + 各校二次定制**，不在任何标准里，无法从网络层观察推出。

## 3. 「获取其它学校信息」的三条真实渠道

1. **本机现场探测（最可靠，零隐私外发）**：`campusnet detect --verbose` 输出抠到的
   指纹 → 人打码后发 issue。README 原话：「最缺的是**更多学校的指纹样本**」，
   标题格式 `[指纹] 学校名 · 认证系统`。这是**众包指纹库**机制，本质仍是「人带
   设备到现场采一次」。
2. **聚合清单**：`YDX-2147483647/best-of-bits` 的「🔑认证校园网」分类收了 29 个
   项目（北理 10.0.0.55 深澜族：`BitSrunLoginGo` 568★、`BITNP/bitsrun` 等），
   `github.com/topics/campus-network` 是另一个入口。这些能给出**「哪些学校用哪族
   协议」的先验**，但项目代码里硬编码的是各校自己的端点/字段，仍需人转写。
3. **本机已有的异校语料**：本项目 `docs/corpus-异校响应语料.md`、
   `docs/campus-portal-survey.md`、`internal/dialect`（锐捷 queryString 表达缺口）
   ——已调研过的样本可直接复用，不必重查。

## 4. 对照本项目：现在做到哪、下一步改哪（按性价比排）

本项目**已有的地基**（比 `campusnet` 更严的部分）：物理源绑定 + 校园 DNS 钉真实 IP
（不被 TUN fake-ip 骗）、TLS 证书主机名校验、探测链路与凭据出口分离、全配置驱动
（`server/login_path/login_form/词表/campus_dns/probe_*` 都 ini 可配）。

**具体缺口与最小改法**：

| # | 缺口 | 建议改法 | 依赖 |
|---|---|---|---|
| 1 | `parsePortalLocation` 丢掉 queryString | 保留完整 `Location` 作为指纹上下文（不用于发请求），供厂商识别/参数抠取 | 小改，纯函数 + 单测 |
| 2 | 只做「指纹命中/不命中」，不产出信息 | `cnal detect` 增加 `--fingerprint`：打印 `Server` 头、`<title>`、命中的独特串、抠出的 `ac_id`/`wlanuserip`/`jsVersion` 等，输出脱敏（IP/MAC/账号打码） | 中改，需新单测 |
| 3 | 没有厂商注册表 | 抄 `campusnet` 的加权打分思路，但**只做「识别 + 出配置草稿」**：内置 4~5 族指纹（Dr.COM/SRun/锐捷/eportal/新版 eportal），每族带一份 `login_form` + 端点 + 成功词表草稿，识别后生成 ini 让人确认 | 中改；**不能自动发登录**（见 §5） |
| 4 | 白名单域名只当探测障碍 | 顺势把它变成诊断信息：面板说明「有些网站能用是白名单放行，不是半通」 | 小改，文档/面板文案 |
| 5 | 众包闭环 | 提供 `cnal detect --report` 生成脱敏指纹样本文本，用户可贴到 issue；仓库建 `fingerprints/` 收样本 | 流程，非代码 |

**不做什么**（沿用规格 §6 的否决）：不做任意表达式/动态 DSL 去「自动适配任意协议」；
`login_form` 现在只接受字面量 + 恰好一个 `{user}`/`{pass}`，这个安全边界不砍——
Srun 那种 challenge + 非标准 base64 + sha1 链**无法用静态表单模板表达**，硬塞进
模板等于把凭据计算逻辑变成配置注入面。真要支持 Srun，得单独写一个 Go provider
（`internal/protocol` 下），不是改配置。

## 5. 硬边界：哪些永远推不出来

- **登录端点与字段名**：`/drcom/login` vs `/cgi-bin/srun_portal` vs
  `/eportal/InterFace.do?method=login`——只能靠厂商识别 + 人确认。
- **密码编码**：Srun 的 challenge/hmd5/非标准 base64/chksum；有的学校还有
  JS 加密、验证码、时间戳签名。这些是服务端与前端约定的，网络层看不到算法。
- **成功/失败词表**：`result:1` / `error:ok` / `Msg=00` / `认证成功` / 本校的
  `success:true`——本项目已有 `[response]` 词表可配，但**必须人填或样本库给**。
- **各校私有参数**：`ac_id`、`service`（运营商）、`queryString`、`vlan`、`ssid`——
  部分能从页面/重定向抠，部分（如选哪个运营商）是用户决策。
- **凭据本身**：学号密码永远只能由用户本机输入（keyring/Keystore），任何「自动
  获取其它学校信息」的方案都不该碰这个。

**结论**：底层原理能把「异校适配」从「人肉抓包 + 手填 10 个 ini 键」压缩成
「跑一次 detect → 确认厂商 → 填账号密码」，但压不到零配置。最诚实的下一步是
先做缺口 #1/#2（把 `Location` query 和 `Server`/页面特征留下来、输出脱敏指纹），
因为它们是后面所有自动化的原料，且**不触碰登录链路、零网络风险**。
