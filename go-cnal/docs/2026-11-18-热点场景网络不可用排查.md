# 2026-11-18 校园网突然不可用排查（手机开热点给 PC 场景）

## 现象

用户报告：校园网突然不能用；手机开热点给 PC，PC 第一时间也上不了网；**把安卓版守护关掉才恢复**。

## 根因（三层，按证据强度排序）

### 1. 直接原因：FlClash TUN 劫持了校园域名（已实测确认）

`nslookup a.stu.edu.cn` 返回 `28.0.0.62` —— 这是 FlClash 的 fake-ip 网段。校园域名被 DNS 劫持成假 IP，所有走域名的校园内网访问（门户、自助页）都指向不存在的地址。只有钉 IP 直连（`--noproxy` → 1.1.1.2:301）能通。

这与 11-13 那次是同一类问题：**加速器 TUN 与校园网共存**。区别是这次更彻底——连 DNS 都被接管了。

### 2. 放大因素：双守护 + 同账号会话争抢

- PC 守护 17:29:35 发了一次自动登录
- 安卓守护同时在跑（用户关闭它后恢复）
- 两设备同账号 → 门户会话互踢（规格 §11.1 的 4 地址配额）
- PC 日志 17:27:26「离线」→ 17:27:29「在线」三秒内翻转，是典型的互踢特征

### 3. 触发场景：物理源切换

`17:28:59 物理源切换: 172.29.153.208 → 10.141.53.34` —— 手机开热点后 PC 从 WLAN 切到以太网，守护重新选源并触发登录。此时 FlClash 正劫持 DNS，登录请求打到 fake-ip 失败，形成「认证服务器不可达」→ 重试 → 撞会话配额的循环。

## 为什么关掉安卓守护就好了

安卓守护在热点场景下的行为链（代码证据 `NetBinder.kt:35`、`KeeperService.kt:105`）：

1. `bindProcessToNetwork(net)` 绑定整个进程到 Wi-Fi
2. 但开热点时手机的 Wi-Fi 是**热点模式**（AP），不是客户端模式
3. `NetPick` 找不到合格的「Wi-Fi 客户端」网络 → `bindProcessToNetwork(null)` 解除绑定
4. 守护继续按默认网络（蜂窝）探测 → 探测失败 → 触发自动登录
5. 手机用蜂窝流量登录校园门户 → **必然失败**，但会消耗门户的登录配额
6. PC 同时在登录 → 两边撞配额 → 互相踢下线

关掉安卓守护后，PC 侧少了一半的登录压力，会话能稳定。

## 修复建议

### 立即（用户侧，零代码）

1. **手机开热点时，关掉安卓守护**（或至少关「自动重连」）。热点模式下守护无法绑定校园 Wi-Fi，只会用蜂窝白撞门户。
2. **FlClash 给校园域名加直连规则**：`a.stu.edu.cn`、`1.1.1.2`、`10.129.17.10` 走 DIRECT，不要进 TUN。这是 fake-ip 劫持的唯一解。
3. PC 与手机**用不同账号**（避免同账号配额互踢）。

### 需要改代码（待拍板）

**A. 安卓守护检测热点模式自动暂停**（与 VPN 暂停同款机制）
- 判据：`ConnectivityManager` 里没有 Wi-Fi 客户端网络，但 `WifiManager.isWifiApEnabled` 或热点接口存在
- 动作：暂停自动登录 + 通知「热点模式，守护暂停（无法绑定校园网）」
- 复用现有 `VpnGuard` 的边沿决策模式，~1h

**B. PC 守护检测 DNS 劫持**
- 判据：`nslookup 校园域名` 返回 fake-ip 段（28.0.0.0/8）或非预期 IP
- 动作：状态里明确显示「DNS 被代理劫持，校园域名不可达」而不是笼统的「出口受限」
- 这是把黑盒变成可解释，与 11-13 的风控可见化同一条产品线

## 诚实边界

- 手机侧日志没拿到（adb offline），「安卓守护触发登录」这一环是**基于代码路径的推断**，不是实测。要确认需手机亮屏后拉 `files/cnalw.log`。
- 「关掉守护就好」这一因果关系是用户观察，与代码路径一致，但没有 A/B 对照。
- 校园侧是否因此次事件冻结账号，未查（需要门户自助页看状态）。
