# 2026-11-11：根因修正（1.1.1.2 就是门户）与门户选源设计

> 起因：11-10 的诊断说「DNS 应答被劫持，守护把 Cloudflare 当门户钉死」，并据此
> 加了「公共解析器地址一律拒绝钉 IP」的判据（提交 `ee0c2d8`）。**11-11 真机复测

> 全文结论均带实测证据；无凭据、无副作用的探测与有凭据的登录分开标注。

## 0. 一句话

**`1.1.1.2` 不是 Cloudflare，就是汕头大学门户服务器的真实地址**（校内路由把它
指向校内门户机）；插网线后守护登录失败的真正原因是**「物理源按路由表选，插线后
选中以太网，而校园认证网关只在 WLAN 网段可达」**。原判据把真门户当成劫持挡在
门外，必须撤销；改用**证书主机名校验**做信任闸，并把选源从「路由 metric」改成
「**门户可达性探测**」。

### 1.2 第二处自我否证（本文写作过程中实测推翻自己的话）

写作本文时先测到「`1.1.1.2:443` 只从 WLAN 源可达，以太网源超时」，并据此把
「认证网关只在 WLAN 网段可达」写成事实。**修完代码、装上守护再复测（02:2x），

且守护随即能拿到门户应答（不再是超时）。

**教训**：有线段到校园认证网关的可达性**随时间变化**（有线网关的路由/ARP
收敛、校园侧策略都可能变）。因此：

- 代码里**不能**写死「认证走 WLAN」「有线走不通」这类静态规则；
- 选源必须**现场探测**，且**失败即重探**（探测结果不能缓存成永久事实）；
- 文档里凡是带「只/永远/必然」的可达性断言，都得标注**测量时刻**。

## 2. 新判据 D1：门户钉点的信任靠证书，不靠 IP 名单

**为什么不用 IP 名单**：校内门户的公开 A 记录就是 `1.1.1.2`；任何「按地址形状
猜是不是门户」的黑名单都会误伤真门户，也无法覆盖「校外出校门时 1.1.1.2 真是
Cloudflare」的场景。

**闸门**：发凭据前必须完成 TLS 握手，且**对端证书对门户主机名有效**。

| 配置 | CA 链 | 主机名 | 适用 |
|---|---|---|---|
| `ssl_verify = true`（默认） | 系统信任库全链校验 | 校验 | 本校门户：实测通过（Xcc Trust OV SSL CA） |
| `ssl_verify = false` | 跳过 | **仍校验** | 自签门户：证书主机名对就能过，冒名证书过不了 |

- 现状是 `ssl_verify = false` 且**完全不做校验** → 校外场景下凭据会发给真
  Cloudflare。这是真实漏洞，本次一并修掉。
- 保留的形状类拒绝（这些**不可能**是门户）：环回、链路本地、未指定、组播、
  非全局单播、fake-ip 段（`28/8`、`198.18/15`）。**公共解析器黑名单删除。**

## 3. 新选源 D2：门户可达性探测

**为什么不能按路由 metric 选**：路由表回答的是「去任意公网走哪条路」，而认证
网关只在**校园网段**可达——有线段的默认路由 metric 更低，恰好选到不能到认证
网关的那条。选源必须以**门户可达性**为准。

**机制**：

1. **候选集**：内核路由偏好源（通常是有线，metric 低）+ 其余非虚拟网卡的可用
   v4 源；顺序即优先级（用户既定决策「有线优先，拔了回 WLAN」）。
2. **探测**：对每个候选做「绑源 → 校园 DNS 解析门户 → 对钉点做 TLS 握手（带
   主机名校验）」。**全程无凭据**。第一个通过的就是当前源。
3. **粘性与自愈**：选中后缓存；该源被门户操作判失败 → 立刻失效，下一拍重探
   （替代 30s 节流），恢复目标 ~1s。
4. **失败要说人话**：所有候选都不通 → 报「候选 N 个，均不可达：<源>（原因）…」。
5. `bind_ip` 手工钉源仍然优先且**不做探测**（用户显式意图优先于自动发现）。

**与既有双路径（`net_mode=auto|bound|system`）的关系**：双路径解决「绑源 vs 系统
栈」，本设计解决「**绑哪个源**」。两者叠加：先选源（可达性），再选路（auto 下
绑源优先、解析失败转系统栈）。

## 9. 顺带查清的另一件事：门户的登录语义（与网线无关）

本轮为查「为什么守护登录不通」读了门户自己的前端（`ac_portal/share/res/js/
logic_new.js`，2026-11-11 实测抓取）与门户应答，得到三条**校事实**：

| 事实 | 证据 |
|---|---|
| 浏览器的密码登录请求带 **`ipv4or6`** 字段（客户端在「另一栈」上的地址） | `logic_new.js` 的 `onPwdLogin()`：`opr/userName/pwd/ipv4or6/rememberPwd`；取值来自 `syncGetIpv4or6()` → POST `opr=ipv4or6online` 到对端 `http://[1::2]/ac_portal/login.php`（v6 对端） |
| 本守护**已经**带上了这个字段 | `protocol.BuildLogin` + `keeper.peerValue()`：双栈开且现场握手取到值就填 `ipv4or6`；实测对端回 `{'success':true,'ip':'2001:250:3003:aa29:56dd:a744:bd21:a019','isOnline':true}` |
| 门户对**直接**发来的 `pwdLogin` 一律回「Task 'NOAUTH:*' not taken」 | 用**不存在的账号**做对照（不碰真账号、无冻结风险）：从两个源、带/不带 `ipv4or6` 共 6 种组合，回包**完全一致**：`{'success':false,'msg':'Task 'NOAUTH:*' not taken',…}` → 该字段不是关键变量 |
| 门户在**免认证时段**（23:30–06:30，守护配置 `free_windows` 同值）会自动放行 | 实测此刻 `opr=online_check` 从两个源都回 `online=1`；守护状态也是「免认证时段」 |
| 守护的登录在**历史上从未成功过** | `cnalw.log` 里 24 次门户级拒绝（18 次 `{'msg':'用户名或密码错误','userName':'…ykyang'}`、3 次「用户被冻结，冻结剩余 60s」）；Python 时代 `keeper.log` 里 425 次 `not taken`、46 次「用户名或密码错误」 |

**由此得到三条未决项（本轮未做，也不该靠猜）**：

1. **凭据是否正确**：`用户名或密码错误` 是门户**受理了登录**之后回的——协议层
   没问题，疑似**密码**对不上（keyring 里那份可能是旧的）。
   > **（已否证，§11.1）**：用户明确「密码是对的」，06:31 守护用**真账号**自己登上；
   > 那些拒绝是**未认证窗口态**的门户瞬时回绝，不是凭据错。
2. **「NOAUTH 任务」从哪来**：门户显然按「客户端地址」维护待认证任务；直连门户
   地址发登录会被拒（not taken），而浏览器是**先被校园拦截跳转到门户**、再提交
   登录。守护的 L1 锚点探针（`http://<锚点IP>/generate_204` + Host 头）在未认证
   时应当会触发同样的拦截——**待验证**。
3. **免认证时段之外才是真正的验收窗口**：23:30–06:30 校园自动放行，任何登录
   尝试都会被回「not taken」（实测），因此**登录成功只能在 06:30 之后验**。

## 11. 免认证时段结束后：真机验收（2026-11-11 06:31 / 09:5x，全部实测）

### 11.1 自动登录（通过）

|---|---|

临时用户 IP——说明这是**真登录**，不是免认证时段的临时放行。

### 11.2 FlClash 开着 + 踢线 → 手动重登（通过）

FlClash 的 TUN 起来后（`FlClash Meta Tunnel` ifIndex 45，v4/v6 默认路由都被它抢成
metric 0），守护仍走「绑源钉 IP」。从门户注销 v4（`{'success':true,'msg':'注销成功'}`，
随后 `online_check` → `{"online":0}`），再点一次 `POST /login`：

- 守护应答 `{"ok":true}`；
- 门户随后 `online_check` → `{"online":1,"username":"<真账号>"}`。

→ **FlClash 常开时登录链路成立**（此前所有验证都是 FlClash 关着做的）。

### 11.3 会话判死用错了信号（已修）

**现象**：注销 v4 后门户已 `online:0`，但守护**仍报「在线」**，不会自动重登
（要靠手动 `/login`）。

**根因（实测）**：判死链（`probeSession`）读 `userflux`——**账号级**读数，会话被
释放后照样回：

```
{"帐号状态":"正常","当天流量":"603.281M","日流量额":"4G","用户名称":"<真账号>",...}
```

于是「flux 有数据 = 会话活着」这条判据在**会话被释放**的场景下永远为真 → 判死永不触发。

**修法**：新增会话级缝 `Daemon.SessionAlive`（`internal/keeper/daemon.go`），接
`onlineV4` 的 `online_check`（按源认栈、**无凭据**、与登录同入口）。未接线时仍回落
flux（异校/旧接线不失效）。

> **（判死去抖又收紧，见《下午收尾落地记录》§3）**：会话级 `online_check` 是权威
> 信号，不该套 flux 的「2 拍」去抖（实测注销后先报「在线」60s 才动手，用户看到
> 「不自动重连」）——现改成**会话级一拍判死、flux 回落仍两拍**。

**验证**：
- RED→GREEN：`TestSessionProbeTrustsOnlineCheckOverFlux`（一拍判死）、
  `...AliveClearsDead...` / `...ErrorNotCounted` / `...FallsBackToFluxWhenUnwired` /
  `TestFluxFallbackStillDebounces`（弱信号去抖未被误删）；
- 变异：把会话级分支短路（`if false && ...`）→ 第一条立刻报红，改回通过；
- **真机复验**：新版本重启后再从门户注销 v4 → **守护自己登回去了**
  （`/state` → `online`，门户 `online:1`），全程无人工干预。

### 11.4 顺带查清：Windows 会自动弹门户登录页（非本项目行为）

排查「开发时浏览器老弹登录页」：`EnableActiveProbing=1`（Windows 强制门户探测开着），
探测 `www.msftconnecttest.com` 被校园门户劫持 → Windows 自动用默认浏览器（Edge）打开
门户页；`PassivePollPeriod=15`、`CaptivePortalTimerMaxInSeconds=30` → 未认证时反复打开。
Edge 历史里能看到门户自己的重定向链（`/` → `index.htm` → `needauth.html` →
`proxy.html` → `pc.html`）与上百次访问计数，而本项目代码只在**用户点托盘
「打开认证页」**时才直接打开 `.../default/pc.html?tabs=pwd`。

处置：已把 `EnableActiveProbing` 置 0（备份与原值/还原命令记在
`%LOCALAPPDATA%\campus-net-autologin\ncsi-backup.txt`）。
