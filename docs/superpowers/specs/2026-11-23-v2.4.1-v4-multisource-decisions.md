# v2.4.1 ① v4 全源会话搬移 — 设计决策台账（grill-with-docs）

> 状态：grill 已定稿（2026-11-23），四项的「做什么/不做什么」已逐条拍板，
> 剩余为实现细节（见各节待办）。本文件逐条记录用户拍板的设计决策，
> 每条含「决策 / 理由 / 被否方案 / 验证点」。
> 上下文：`go-cnal/docs/2026-11-23-双网卡切账号会话分裂复盘.md`（根因+代价）。

## 领域术语（先钉词，避免实现时漂移）

| 词 | 定义（本项目内唯一语义） | 非此词 |
|---|---|---|
| 会话搬移 | 切账号时把某本地源在门户上挂的旧账号会话，改为新账号：注销旧会话→登录新账号→门户回读确认归属 | 单纯「换凭据」「Relocate」 |
| 物理源 | 物理网卡上的可路由地址（WLAN `172.29.x` / 以太网 `10.141.x`），门户按它记会话 | Clash/TUN 的 fake-ip、虚拟网卡地址 |
| 主源 | 守护 `DiscoverSource` 选出的当前 v4 物理出口（authenticate 已验活） | 额外源 |
| 额外源 | 本机其它物理网卡的 v4 出口；浏览器默认路由出口通常是其中之一 | 同网卡的次要 IP（当前设计不覆盖） |
| 全源 | 所有物理网卡的 v4 出口（用户 2026-11-23 拍板） | 仅主源+默认路由出口两个 |
| 验活 | 登录后 `online_check` 回读门户，确认该源在线且归新账号（v6 `bindV6` 同款纪律） | 发完登录就当成功 |

## 已定决策

### D-01 范围 = 所有物理网卡 v4 出口
- 决策：`①` 覆盖每张物理网卡的 v4 出口，不止主源+默认路由。
- 理由：用户拍板；双网卡是实测环境，三网卡/多 IP 也应正确，避免再次「新环境触发既有边界」。
- 被否：仅两源（漏三网卡）、仅文案（不修 bug）。
- 验证点：双网卡现成环境切账号 → 两源 + 浏览器 IPv4 门户首页归同一账号。

### D-02 注销策略 = 逐源先探归属再注销
- 决策：每个源先 `online_check` 读归属；仅「在线且归旧账号」才注销，不在线/已归新账号跳过。
- 理由：用户拍板；在解决 D6 限频风险的同时减少总请求数（已归新账号的发注销纯属多余且撞限频）。
- 被否：逐源盲发 logout（N 源 N 次盲注销，限频风险最大）；只搬额外源（两路径不对称）。
- 约束：探归属失败 ≠ 跳过注销的充分理由？——留作下一枝 grill（读失败时的降级策略）。
- 验证点：切账号后所有源归新账号；日志可数出每源请求数，无 D6「用户名或密码错误」误报。

### D-03 验活 = 每源登录 + 回读成对
- 决策：每个额外源登录后 `online_check` 回读，确认在线且归新账号才算成功；失败如实进切换回报。
- 理由：用户拍板；2026-11-10 v4 老事故教训——「登录被答已在线但归属没改」必须靠回读发现。
- 被否：只验主源（可能留「表面成功、实际未改」）；告警不阻断（太弱）。
- 验证点：人为让某源归属不改（测试替身），回报必须报「该源归属未确认」。

### D-04 读归属失败降级 = 仍盲发注销 + 标未确认
- 决策：某源 `online_check` 读失败时，退回 11-10 铁律照发 logout，回报标「该源归属未读清、已尝试注销」。
- 理由：用户拍板；安全优先于限频，绝不静默跳过注销重演 11-10 归属未改。
- 被否：跳过注销（违背铁律）；重试一次再定（多一次请求且未消除不确定性）。
- 验证点：测试替身让某源读归属报错 → 该源仍收到 logout 请求，回报含「未读清」字样。

### D-05 限频控制 = 源间短暂节流（300–500ms）
- 决策：每个源处理完后 sleep 300–500ms，避免瞬间连发；不做复杂退避/重试。
- 理由：用户拍板；D6 成因未定案，不把猜测写进代码；Simplicity First。
- 被否：失败退避重试（把「成因不可辨」编码进逻辑，可能延长限制窗）；先不加（用户要主动防）。
- 验证点：真机切账号无 D6「用户名或密码错误」误报；日志时间戳可见源间间隔。

### D-06 失败语义 = 整体仍成功，失败进回报
- 决策：主源成功即算切换成功；额外源失败写进回报文案，不改 /accounts 契约。
- 理由：用户拍板；沿用现状「凭据已落地不算切换失败」语义，面板/API 零改动。
- 被否：额外源失败返回 error（主源成功却标红会误导，且改契约）。
- 验证点：额外源验活失败时回报含「归属未确认/浏览器可能仍显示旧账号」，返回值 err=nil。

## ② extra v6 补绑偶发被拒 — 设计决策

### D-07 性质 = 先诊断定性，再决定动不动代码
- 决策：② 先复现并拿门户原始 message + 当时操作时序（快速连切？冻结窗？），确认是 D6 瞬时限频后再定方案；不预设要改代码。
- 理由：用户拍板；D6「成因不可辨」的教训就是不能凭单次现象归因，Simplicity First。
- 好消息（代码探索确认）：门户原始 message **已透传**（日志 `登录未受理: 用户名或密码错误` 即门户原文），诊断不缺数据，缺的是复现时序对照。
- 现象锚点（复盘 §6-2）：切回 23ykyang 时 extra v6（隐私临时地址 `:d266`）补绑报被拒，但紧接「门户确认 v4/v6 都归 23ykyang」——主会话不受影响，失败仅限 extra v6。
- 待查（诊断项）：补绑是否撞快速连切限频；是否 IP 级冻结窗；是否可加退避重试。
- 验证点：拿到至少一次复现的完整时序（前一次切换时刻→补绑时刻→门户回包 message），据此定性。

## ③ 注入模式 IP 变了自愈（安卓 P1）— 设计决策

代码事实（探索确认）：
- Go `SetPhysicalSources` 可重入（inject.go:84 加锁可反复调）；
- 注入模式下 rediscoverer 不创建（compose_portal.go:232 注释「bind_ip 手工钉源 / 安卓注入源时为 nil」），Go 无自愈；
- `currentV4()` 注入模式直接返回注入值（compose_portal.go:94-96）；
- Kotlin 只在启动/探测时调 `injectSources`（CnalKernel.kt:197,225）；
- a725422 已加 `Client.Bindable(src)` 每拍自检（注入源过期时 Bindable=false）。

### D-08 修复层 = Kotlin 主修 + Go 兜底
- 决策：两者都做。Kotlin 注册 ConnectivityManager.NetworkCallback（onAvailable/onLost）重新取 LinkProperties 的 v4/v6 并重注入；Go 侧绑源失效时通知 Kotlin 重注入。
- 理由：用户拍板；源归属 Kotlin，主动权在 Kotlin；Go 兜底覆盖 NetworkCallback 漏掉的场景。
- 被否：仅 Go 重发现（注入模式的存在理由就是 Go 发现不准，可能拿错源）；仅 Kotlin（用户要兜底）。
- 验证点：换 WiFi / 路由器重启后，无需重启守护，1 拍内恢复在线。

### D-09 Go 触发 = Bindable=false 时经缝通知 Kotlin
- 决策：复用 a725422 的 `Bindable` 自检点，注入源不可绑时调新缝 `SourceStale` 通知 Kotlin 取新源重注入；与 bind 修复共用传感器，不重复造。
- 理由：用户拍板；单一检测点，符合手术式改动。
- 被否：Go 自己 DiscoverSource（注入模式下可能拿错源）；只靠 Kotlin（与 D-08 冲突）。
- 验证点：测试替身让注入源 Bindable=false → SourceStale 回调被触发一次（不重复风暴）。

## ④ 手机端配置自助维护（安卓 P2）— 设计决策

代码事实（探索确认）：
- `/config` 端点 + 面板设置页已能改 ssl_verify 和凭据（advanced.go / compose_api.go），**但只在守护运行后可用**；
- release 版不可 debuggable，换机/重装首启无法 `run-as` 写 filesDir/config.ini；
- 凭据存 Keystore、ini `[accounts]` 只含用户名+server，不含密码。

### D-10 性质 = 首启引导加配置文件导入
- 决策：给首屏加「导入配置」入口，用户选一个 config.ini（含 server / ssl_verify / [accounts]）写入 filesDir 后再启动守护。
- 理由：用户拍板；一次性解决换机/重装首配，不必依赖 run-as 或多步 SOP。
- 被否：纯图文 SOP（多步易错）；先验证是否真痛点（用户已确认是痛点）。

### D-11 导入安全 = 先校验再写盘，失败给明确原因
- 决策：导入时复用现有 ini 解析 + advanced.go 校验（server 格式 / ssl_verify 布尔 / [accounts] 结构），非法文件拒绝并指出哪一行错；只导入白名单键，忽略未知段。
- 理由：用户拍板；防止错配 ini 让守护启动失败且难排查；凭据不进 ini（Keystore 依旧）。
- 被否：纯文本替换不校验（错配难排查）；只导入两项不导账号（换机要手动重加，未解决痛点）。
- 验证点：导入非法 ssl_verify 值 → 拒绝并提示行号；导入合法文件 → 守护按新配置启动。

## 跨项实现细节（不阻塞设计，留给实现阶段收敛）

- ① 实现方式：`sessionOps` 扩展（新增 `v4Sessions` 切片仿 v6Release）vs 临时 `Client.SetSource` 切源。
- ① 源枚举：`netstack` 新增 `V4Sources()` 的筛子——沿用 `DiscoverSource` UDP 出口法还是枚举网卡地址表（须排除虚拟网卡）。
- ① 顺序：v4 多源与 v6 搬移的先后、与 authenticate 的相对位置（v4 注销贴近认证前一刻少断网）。
- ③ Kotlin NetworkCallback 与 Service 生命周期绑定；SourceStale 回调节流/防抖（防 Bindable 抖动引发重注入风暴）。
- 流水线约束（四项通用）：每项实现后走 trouble-maker → tester → 真机复测（复盘 §6 约束）；① 的双网卡环境现成可复测。
